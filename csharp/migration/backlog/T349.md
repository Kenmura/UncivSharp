### T349 Per-unit GetViewableTiles cache keyed on position, range and a terrain revision counter
- State: Needs-Review [DeepSeek-T349]
- Depends: none
- Source: Owner-approved candidate 14; design/PERFORMANCE.md (top allocator after T262)
- Fixtures: none
- Deliverables: Cache with correct invalidation (terrain revision counter); byte-identical game state on the soak and golden tests; measured allocation and turn-time improvement; read-only-guard test like T296
- Gate: dotnet build -warnaserror && dotnet format --verify-no-changes && dotnet test
- Claimed: 2026-11-05T11:23Z
- Notes:
  - - Implemented per-unit cache in `MapUnit.UpdateVisibleTiles` for the normal (blocked-by-terrain) branch only; the `NoSight`/`CanSeeOverObstacles` branches are unchanged. Key: map instance, position, sight range, `TileMap.TerrainRevision`, world wrap, shape, map radius/width. A hit returns without replacing `ViewableTiles`, so it writes nothing (T296 rule); a miss stores the `GetViewableTiles` list and copies it to the set.
    - `TileMap.TerrainRevision` is internal and transient (`[JsonIgnore]`, not in the state hash). `Tile.SetTerrainFeatures` is the only writer of `UnitHeight`/`TileHeight` and bumps it, but only when the tile is the map's own instance at that position (clone/display tiles share the `TileMap` reference and must not invalidate).
    - Tests: new `Unciv.Core.Tests/Logic/Map/ViewableTilesCacheTests.cs` (4 tests): terrain change without movement recomputes and the hidden forest becomes visible; moving the unit recomputes; a `[+2] Sight` promotion recomputes at range 4; a second call with the same key leaves `ObjectGraphFingerprint.Of(GameInfo)` byte-identical (T296-style read-only guard). Existing `TileMapTests`, `MapUnitCoreTests`, `ViewBuildingReadOnlyTests` also pass.
    - Gate on the rebased tip: build + format + `ptest` 8899 passed, 0 failed, 6 skipped + coverage ratchet passed. (The first full gate had one failure, `NetLobbyTests.ServerLobby_KnownKeyDuringStarting_Waits...`, a known flaky test tracked as T314; it passed alone and in the two later full gates.)
    - Golden: `dotnet Unciv.Cli/bin/Release/net10.0/Unciv.Cli.dll bench --scenario all --golden migration/design/perf-golden.json` -> `golden small: 50 turn hashes identical`, `golden medium: 200 turn hashes identical`. Every interleaved 50-turn small run also had hashes identical to its base run.
    - Measurements (Release, `bench --scenario small --turns 50`, base and after binaries built separately and run alternately in one session; base = parent of the implementation): allocation is the robust number, total per run 773.0/773.1/773.1 MB base vs 718.2/718.3/718.5/718.7 MB after (~-7.1%); late-quarter allocation 22.99 vs 21.4 MB/turn (~-6.9%). In an idle pair the `UCS.UnitVisibleTiles` phase went 11.99 ms / 1.9 MB -> below the top-12 cutoff (<7.82 ms / <1.4 MB), and `RefreshTransientCaches` allocation 10.3 -> 8.7 MB. Wall time on this shared machine is noisy: the three idle pairs gave late medians 154.9/168.2/173.4 ms base vs 160.3/149.7/130.8 ms after (median 168.2 -> 149.7, about -11%), while three pairs run under heavy load showed larger, unreliable gaps (pooled median 305.9 vs 164.6); treat the turn-time gain as small/uncertain and the allocation gain as measured.
    - Not run: the 300-turn `Category=Soak` games (each up to 25 min, and Bnw300 has a pre-existing save/reload failure tracked as T293). The full gate runs the 80-turn BNW save/load+replay variant and the determinism suite, and the 200-turn medium golden covers the long-run state equality.
