  - Root causes found (all four reported flake families), with the fix in this branch:
    1) NetLobby's named flake was the T364 over-strict `Assert.All(joins, j => j.Joined)`: the newer same-key connection may close the older one before its JoinOk, so the older JoinResult is legitimately `connection-lost` (historical gate log from 2026-10-29, captured verbatim in the T279/T364 session logs). T364 already relaxed it to `Assert.Contains`; this ticket verifies it. Two more real timing races were still present and are fixed here:
       - NetLobby helper `ReceiveMessageAsync` defaulted to a 2 s failure bound and let a cancelled receive surface as `OperationCanceledException`; under the gate the App shard runs beside 7 other processes and frames can take longer (this exact failure appeared in a gate run while implementing this ticket: `ServerLobby_KnownKeyDuringStarting_...` OCE). Default is now 30 s (failure-only), snapshots use 30 s, and a cancelled receive becomes the intended `TimeoutException`.
       - `ServerLobby_ClientSession_...`, `ServerLobby_SecondConnectionOfTheSameKeyBeforeStart_...` and `...TwoRapidSameKeyReconnects...` submitted an EndTurn immediately after `StartGameAsync`, which returns before the client applied its first snapshot (empty ClientCmdId -> false), and the rapid-reconnect test used a fixed 2 s submit. All now wait for the connection the host kept (`WaitForSeatedSessionAsync`: exactly one ClientSession in `InGame`, bounded by Bound), then submit; the assertions (someone joined, exactly one Rome session, that session is playable) are unchanged. The old `AnyTrueAsync`/`TrySubmitAsync`/`WaitForSnapshotAsync` helpers are gone.
    2) The "4 server/CLI bench failures" (T308 gate 2026-10-30) were ptest workspace clobbering, not test logic. `ptest.py` gave every invocation the same `.coverage/bin/shardN` private copies and `.coverage/raw` results dir, and `private_copy`/`run_shard` rmtree them at startup. Two ptest/gate runs in one worktree therefore delete each other's live coverlet-instrumented assemblies and TRX files. The historical failure pattern matches exactly: 2 BenchTests with empty output/exit 1 (`HelpAndBadOptions`, `GoldenFileMatches...`), 2 DedicatedServerTests with `FileNotFoundException`, and two core shards reporting `0 failed (exit 1)` (their TRX had been deleted). Reproduced before the fix by running two concurrent `ptest --coverage --class BenchTests DedicatedServerTests` in this worktree: 33 tests failed with `SecurityException: Invalid assembly public key` and the other run's test host crashed, `23 passed 0 failed (exit 1)`. After the fix the same two concurrent runs both pass 40/40, and two concurrent coverage runs of NetLobbyTests+StandbyListenerTests+BenchTests+DedicatedServerTests both pass 79/79.
       Fix: every ptest invocation gets its own workspace `migration/.coverage/run-<pid>-<ns>/` (private bin copies and default results), removed on exit (`--keep-tmp` keeps it and prints the path). Explicit `--results` still wins. Added unit tests in `tools/test_ptest.py` for per-invocation names and that private copies live inside the run workspace; documented in PROTOCOL T013.
       Also moved BenchRunner's `cli.RejectUnknown()` + scenario validation before `loadRulesets`, so `bench --scenario huge` is exit 2 even if the ruleset files are momentarily unreadable (its argument test no longer depends on assets).
    3) `StandbyListenerTests.ASecondHello_IsRefused_AndAnIdleConnectionIsClosedAfterItsLifetime` used one 300 ms `ConnectionLifetime` for both the frame exchange and the idle-close assertion. Under load the TLS handshake + first Hello could exceed 300 ms, so the listener closed before Welcome (historical gate: `Assert.IsType<Welcome>` Value null). The frame exchange now uses a 60 s lifetime; a separate 300 ms listener still asserts that an idle connection is closed after its lifetime. `ReadAsync`'s failure bound is 30 s (was 5 s). Meaning of both assertions is unchanged.
    4) T376's StandbyReplication/RelayClient/HostHandoff timeouts were the same load-bound family; T402 already raised those failure-only bounds to 120/180 s, and the ptest isolation above removes the corrupted-output cause. No quarantine used.
